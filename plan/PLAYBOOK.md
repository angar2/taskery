# PLAYBOOK — 미래 옵션 카탈로그

> 진짜 데이터 / 짜증 / 시점에 따라 부활시킬 *미래 옵션* 인덱스.
> **선제적 작성 금지. 진짜 필요해질 때 찾아 추가.**

---

## 사용 방법

- 평소 불편/한계는 `.project/FRICTION_LOG.md`에 기록 (`/log-friction` 스킬이 한 행씩 추가)
- 사용자가 직접 FRICTION_LOG.md를 정독해 누적 패턴 검토
- 검토 결과 본 카탈로그에서 부활 후보 항목 발견 시 사용자가 부활 결정
- 부활 항목의 **방법** 따라 도입

각 항목 형식:

```markdown
## <주제>
- **상황**: <언제 이게 필요해질지>
- **요소**: <무엇을 추가할지>
- **방법**: <어떻게 도입할지>
- **얻는 것**: <효용>
- **주의**: <함정/조건>
- **출처**: <시니어 패턴 / bottoms-up / 등>
```

## 1. 컨텍스트 격리 강화 (Task tool default 확장)

- **상황**: 30+ task 누적되어 메인 세션 컨텍스트 폭발 직전. `/task-plan`, `/task-dev` 같은 스킬도 격리 필요해짐
- **요소**: `/task-test` 외 스킬도 default를 *Task tool 격리*로 옮김. 스킬별로 부담 큰 곳 지정
- **방법**:
  1. FRICTION_LOG에서 *어느 스킬이 컨텍스트 부담 큰지* 통계
  2. 후보 스킬(예: `/task-plan` 큰 코드베이스 탐색 시) instruction에 *"기본 Task tool 격리 호출"* 추가
  3. 격리 prompt에 task.md 경로 + 필요 컨텍스트만 명시 (자기완결적)
- **얻는 것**: 메인 세션 컨텍스트 절감. 30+ task 굴려도 압축 회피
- **주의**: 격리 prompt가 *자기완결적*이지 않으면 격리 세션이 가정 헛돌릴 수 있음. prompt 디자인 필수
- **출처**: 시니어 패턴 (의도 파악만 메인, 구현 위임)

## 2. 압축 평가 기준 subagent (유사 RAG)

- **상황**: 제품 관통 문서 + 코드 컨벤션 누적되어 task별 *관련만 골라내기* 부담 ↑
- **요소**: 메인이 task 시작 전 *압축 평가 subagent* 호출. 그 task와 관련된 기획 문서/코드 영역만 추출해 메인에 전달
- **방법**:
  1. Task tool로 *"이 task 주제에 관련된 기획/코드 영역 추출"* 요청
  2. subagent가 제품 관통 문서 정독 → 관련 부분만 발췌
  3. 메인이 발췌만 받아 작업 — 9 문서 전체 메인 컨텍스트 X
- **얻는 것**: 큰 프로젝트에서도 메인 컨텍스트 가벼움. RAG 효과
- **주의**: subagent가 *놓친 부분* 위험. 발췌 누락 시 메인이 잘못된 가정. fallback으로 메인이 직접 살펴보는 옵션 유지
- **출처**: 시니어 패턴 (서브에이전트 = 평가 기준 / 핵심 파일 추출 / 압축)

## 3. Python orchestrator + `claude -p` 헤드리스

- **상황**: task당 phase 100개 단위 풀 자동화 시나리오. 4 중단점 대화 흐름이 부담스러워질 때
- **요소**: Python 스크립트가 phase별 `claude -p` subprocess 호출. JSON 인덱스로 재시작/복구
- **방법**:
  1. `bin/orchestrator.py` 작성. phase 인덱스 JSON 관리
  2. 각 phase = `subprocess.run(["claude", "-p", prompt])` 호출
  3. 실패 phase 재시도, 성공 phase 인덱스 저장
- **얻는 것**: 자동화 극대화. 사용자 간섭 0
- **주의**: **현재 정신과 충돌** — 4 중단점 대화가 *주 use case의 핵심*. 풀 자동화는 강제 분담 함정 재발 위험. 진짜 phase 100+ 시나리오 *발생할 때만* 검토
- **출처**: 시니어 패턴 (subprocess + claude -p)

## 4. minimal form hook

- **상황**: 태스크 문서 형식 위반(헤더 누락 / 섹션 빠짐)이 *진짜 프로젝트에서* 짜증 패턴으로 5회 이상 누적
- **요소**: PreToolUse(Write|Edit) hook으로 task.md 헤더 5컬럼 + 6 섹션 존재만 검증. 통과 못 하면 차단
- **방법**:
  1. `.claude/hooks/form-check.sh` 작성 (40~50행 이내)
  2. tasks/*/*.md 변경 시 헤더 표 + 6 섹션 헤딩 grep
  3. 둘 중 하나라도 누락 → exit 2 + 메시지
- **얻는 것**: 형식 일관성 회복
- **주의**: **합리적 변형 차단 함정 주의** — 내용 검증 화이트리스트가 합리적 변형까지 차단해 망가지는 패턴이 있음. *섹션 존재* 검사만, *내용 검증 X*. 진짜 짜증 누적 후 도입
- **출처**: form 강제 hook 폐기 후 instruction 1차 — bottoms-up 보강용

- **주의**: 자동 생성된 task가 *waterfall phase 선제적 작성* 함정 재발 위험. 단일 task만 생성, phase 선제 작성 X

- **주의**: **PR 자동 머지는 현재 정신과 충돌**. 리뷰만 자동, 머지 결정은 사용자. 자동 fix도 사용자 confirm 한 단계 필수

## 9. 머지 로직 엣지 케이스 보강

- **상황**: `npx @angar2/taskery update` 시 사용자 customize 충돌 빈발 — 자동 머지가 의도한 customize 깨뜨리는 케이스
- **요소**: `bin/update.js` 머지 로직에 엣지 케이스 처리 추가
- **방법**:
  1. FRICTION_LOG에서 머지 충돌 케이스 수집
  2. 패턴별 처리 분기 추가:
     - 사용자 customize 부분만 보존 + 코어 부분만 갱신 (3-way merge)
     - `*.local.md` 분리 권장 메시지
     - rebase 모드 (사용자 변경 위에 코어 변경 얹기)
  3. fallback = 항상 *.bak 백업 + 사용자 confirm
- **얻는 것**: 동료 사용자 마찰 ↓
- **주의**: 3-way merge 복잡도 ↑. 진짜 충돌 패턴 데이터 5건 이상 모인 후 도입. 데이터 없이 추가하면 over-engineering
- **출처**: bottoms-up

## 10. task-plan Step 3 조건부 Explore 위임

- **상황**: 큰 코드베이스에서 task-plan 진행 시 Step 3 (Scope 코드 서치) 단계가 광범위 grep + read로 메인 컨텍스트 부담 발생. Claude Code 본체 가이드(*"3+ queries → Explore 서브에이전트"*)에 따라 *자율 판단*으로 Explore가 자동 호출되는 현상은 이미 발생 중이나 taskery 측 명시 부재로 메인 세션마다 *위임/직접* 결정이 흔들림. 일관성 부재 마찰 누적 시
- **요소**: task-plan SKILL.md Step 3 본문에 *위임 판정 휴리스틱* + *announce 룰* 추가. Step 3에 한정한 *조건부 권장* — 강제 X, 사용자 confirm X
- **방법**:
  1. Step 3 본문 상단에 *판정 표* 추가 — 영역 수 + 키워드 구체성 두 신호 조합:

     | 신호 | 방식 |
     |------|------|
     | Requirements에서 3+ 영역/모듈 언급 | Explore 서브에이전트 위임 |
     | 정확한 함수/파일 위치 불명 — 키워드만 | Explore 서브에이전트 위임 |
     | 단일 파일 / 명확한 함수 위치 명시 | 메인 직접 Grep/Read |
     | 작은 fix — 변경 위치 사전 확실 | 메인 직접 Grep/Read |

  2. 판정 후 *announce 한 줄* 룰 — *"광범위 탐색 판정 → Explore 위임 (근거: <영역 N개 / 키워드 모호>)"*. 사용자 confirm X. announce 근거만 공개
  3. 경계 케이스 default = 메인 직접 (안전쪽). 직접으로 시작했다 광범위 판명 시 그 자리에서 Explore 전환 허용
  4. SKILL.md Step 3:327 *디자인 산출 정독 sub-agent 금지* 룰 옆에 *범위 명시 한 줄 추가* — *"Step 3 코드 서치 영역의 sub-agent 위임은 별개 정책"* — 금지 범위 모호성 차단
- **얻는 것**: Step 3 컨텍스트 절감 일관 보장. 메인 자율 판단 흔들림 차단. 큰 코드베이스 task-plan 부담 ↓. 디자인 산출 금지 룰과 영역별 정책 대칭 확보
- **주의**:
  - *작은 task에 강제 위임*은 오히려 손해 — 휴리스틱이 *광범위 판정*에서만 위임으로 흐르도록 조정 필수
  - 휴리스틱 경계 케이스는 *메인 직접 default*로 안전쪽. 격리는 *명백히 광범위할 때만*
  - Claude Code 본체 가이드(*"3+ queries → Explore"*)와 정합 유지 — 충돌 시 본체 가이드 우선
  - 9 스킬 전체 정밀 검토 결과 격리 적합 후보는 *Step 3 하나*로 좁혀짐. §1 *전체 default 확장*은 사실상 *비어있는 방향*으로 드러남 — 본 항목이 §1보다 *더 정밀하고 즉시 검토 가능한 단계*
  - **부활 트리거 신호**: FRICTION_LOG에 *task-plan 컨텍스트 부담* 또는 *Step 3 일관성 깨짐* 패턴 누적 시. 지금 마찰 신호 X → 발견 사항 보존만, 부활 X
- **출처**: 본 대화 (2026-06-09) — Claude Code 본체가 Explore 자동 호출하는 현상 발견 + taskery 측 명시 부재 발견. 명시 가이드 확보 차원

## 11. 코드베이스 / 로직플로우 맵 (brownfield 흡수 + 코드 이해 산출물)

- **상황**: 셋 중 하나라도 마찰로 누적될 때 —
  - (a) **brownfield 중간 도입**: 이미 진행 중인 프로젝트에 taskery를 중간 설치. 선제 기획(project-init/plan-init) 없이 출발해야 하는데, 제품 관통 문서를 *사후에* 작성하면 코드를 움직이지 않는 허구 문서가 되고 콜드스타트 비용이 큼.
  - (b) **greenfield 누적**: task 수백 누적 시 매 task-plan Step 3가 코드 재발견(grep/read)으로 메인 컨텍스트를 반복 소모.
  - (c) **§12 검증 기준 부재**: 테스트가 "정상 동작/구조"를 대조할 기준이 없음.
- **요소**: 코드베이스 구조 + 로직/데이터 흐름을 담은 *지속 산출물* 1종. 기존 코드를 읽어 맵을 산출하는 brownfield 진입 모드(기획→코드의 *역방향*). plan-init 의존을 하드 → 선택/지연으로.
- **방법**:
  1. `brownfield-init`(가칭) — 기존 코드를 흡수해 경량 맵 산출. project-init/plan-init의 역방향(코드→문서).
  2. 맵에 담는 것: 모듈 경계 / 진입점 / 데이터 저장소 / 주요 흐름 — *느리게 변하는 구조 사실*만. 휘발성 디테일 제외.
  3. task-plan Step 3가 맵을 먼저 참조 → 즉석 재발견 최소화.
  4. task 흐름이 기획 문서 없이도 코드 + 맵에서 출발 가능하게 (plan-init 선택화).
- **얻는 것**: 동료/기존 프로젝트 진입 장벽 ↓. 매 task-plan 컨텍스트 절감. §12에 검증 기준 제공.
- **주의**:
  - **staleness 계약이 핵심 난제** — 수동 유지 맵은 즉시 썩고, 썩은 맵은 거짓 확신을 낳아 *없는 것보다 나쁨*(§12 실패모드 재발). → 자동 갱신이거나, *느리게 변하는 구조 사실만* 담아 갱신 빈도를 낮추거나. 스킬(task-close 등)이 유일한 갱신 주체인 닫힌 시스템이면 위험 ↓ (`.taskery-manifest.json` 패턴).
  - **미숙성 주의** — 현재 스케일(수십 task)엔 평평한 목록 + 좋은 제목으로 충분. 수백 task / 동료 도입 트리거 전 선제 구축은 over-engineering.
- **링크**: §12(맵 → 검증 기준 제공), §13(brownfield와 "선제 버전 기획 거부" 불평을 공유하나 해법은 별개).
- **부활 트리거**: FRICTION_LOG에 *task-plan 코드 재발견 반복 부담* 또는 *기존 프로젝트 도입 콜드스타트* 패턴 누적 시. 지금은 신호 약함 → 발견 보존만.

## 12. task-test 오라클 강제 (거짓 PASS 차단)

- **상황**: **이미 발생 중인 마찰.** task-test가 유의미한 검증 없이 PASS 도장을 찍음. "빌드/타입 테스트 제외 + 유의미 테스트" 지시로 한 번 고쳤으나 여전. 원인 — LLM 테스터는 *반증 가능한 판정 기준(오라클)* 이 없으면 코드를 읽고 "맞는 것 같음 → PASS"로 낙관에 기움. 즉 **PASS가 너무 쌈.**
- **요소**: PASS 조건을 *증거 기반*으로 강제. "오라클 없으면 PASS 금지, UNCERTAIN" 룰을 task-test SKILL에 명시. (*오라클 = 결과의 옳고 그름을 판정하는, 틀리면 실제로 FAIL이 나는 기준.*)
- **방법**:
  1. **PASS = 증거 있을 때만** — *실제 관측한 동작*이 *실제 기대*와 일치한 증거(실제 명령 출력 / 실제 UI 관측 / 실제 단언 결과). 코드 정독 "그럴듯함"은 PASS 불가.
  2. 증거를 구성 못 하면 FAIL이 아니라 **UNCERTAIN** (실패와 미검증을 구분).
  3. Test Plan 작성 단계(task-plan)에서 각 항목에 *falsifiable 체크*(틀리면 실제 FAIL이 나는 검사) 요구 — "확인한다" 같은 모호 표현 금지.
  4. 빌드/타입 등 *반증력 약한* 검사 제외 방향은 유지하되, "유의미"의 정의를 *오라클 유무*로 못박음.
- **얻는 것**: 거짓 확신 제거. taskery 핵심(메인 세션 confirmation bias 차단)이 검증 단계에서 실제로 작동.
- **주의**: UNCERTAIN 남발로 도망가는 역효과 주의 — UNCERTAIN은 *증거 구성이 진짜 불가*할 때만이며 게으름의 핑계가 아님. UNCERTAIN 시 "왜 오라클을 못 만들었는지" 근거 의무.
- **링크**: §11(맵이 검증 대상/기준 제공).
- **상태**: 미래 옵션이 아니라 *적용 대기열 1순위*. 거짓 확신은 가드레일 시스템의 심장을 침.
- **출처**: 본 대화(2026-06-26) — 원안 #3. 이전 "빌드/타입 제외" fix의 후속(근본 원인 = PASS가 너무 싸다는 점).

## 13. plan = 기능 그룹 재정의 (버전 탈피)

- **상황**: **이미 발생 중.** plan을 버전(vX.X) 단위로 뒀으나, 실사용에서 버전은 임의로 정해지고 잦게 범프되어 의미가 약함. 실제 작업은 *기능 그룹*("내 상품 비교" 메뉴 등) 단위로 묶임 — 버전으로 두기엔 작고 task로 두기엔 큼.
- **근본 진단**: 현재 "plan"이 *두 축*을 겸함 — (A) 제품 스펙 스냅샷(SERVICE-POLICY/FEATURES, 버전 단위가 자연스러움) + (B) 작업 묶음 단위(기능 그룹, 버전과 무관). 한 단어가 둘을 겸해 어긋남이 발생.
- **요소**: plan을 *기능 그룹* 단위로 재정의. 버전은 릴리스 태그로 강등(계획 단위 아님). 자투리(급한 버그/오타/의존성 업데이트)는 *무소속* 허용.
- **방법**:
  1. **대부분 관습/문서** — taskery는 이미 plan 이름이 자유(plan-init: "v1.0/alpha/mvp 등 자유"). plan 폴더를 기능 그룹명으로 쓰면 task/BACKLOG가 그 밑에 nest됨. plan-init·CLAUDE.md·AGENTS.md 톤을 "버전마다 plan" → "기능 그룹마다 plan"으로 전환.
  2. **자투리 = 무소속** — 그룹에 안 묶이고 검색에서 기본 제외(검색 가치 ~0). "유지보수" 가짜 그룹·버전 잔존 양동이는 모두 기각(가짜 그룹은 되찾을 의미 없고, 버전 잔존은 죽이려던 개념을 되살림).
  3. **코드 점검 1곳** — "활성 plan 감지"(lib.js `getBacklogPath`의 activeVersion 등)가 자유 이름을 견디는지. semver 정렬로 *최신*을 고르는 방식이면 기능 그룹명에서 오작동 가능 → 활성 그룹 선택을 *명시*로(task-init/add-backlog가 기본값 + 한 줄 확인, 다르면 그 자리서 전환).
- **얻는 것**: 작업의 자연 단위(기능 그룹)와 계획 단위가 일치. 끼어드는 버그가 그룹 목록을 어지럽히지 않음(전역 TASK-NNN이 이미 순서를 소속과 분리).
- **주의**: **검색/인덱스 인프라는 지금 만들지 말 것** — 폴더는 원래 "지시 세션의 과거 task 검색 인덱스"였으나, 현재 스케일엔 평평한 목록 + 제목으로 충분. 정교한 그룹 검색은 수백 누적 후(§11과 함께). 본 항목은 *구조 대공사가 아님* — 관습 + 문서 + 활성 감지 점검 한 곳.
- **링크**: §11(brownfield와 "선제 버전 기획 거부"를 공유).
- **상태**: **적용 완료 (2026-06-27).** 본구현은 "관습/문서 전환"보다 컸음 — 문서 3분할(그룹 A 작성/B 골격/C plan 로컬, 루트 평평), plan 폴더 `NNN_slug` 채번(`computeNextPlanNumber`), 분기 2(카피포워드) 폐기, delta 깊이 분리(plan-init=의도 stub / task=스키마·엔드포인트 본문), closed-immutable 정규식 `v[^/]+`→`[^/]+` 완화. 상세는 코드/스킬/룰이 단일 진실(여기 재기록 X).
- **출처**: 본 대화(2026-06-26) — 원안 #4. plan의 두 축 겸함 진단 + "폴더는 사실 검색 인덱스였다"는 정체 규명을 거쳐 "대부분 코드 불필요"로 좁혀짐. (구현 시 코드 작업이 예상보다 더 필요했음 — 위 상태 참조.)

## 14. 폴더 승격 — 자동 기본 해제 (사용자 명시 한정)

- **상황**: 현재 폴더 승격(`TASK-NNN_slug/task.md`)이 *규모 large면 자동 기본*(task-init 조건 (a) / TASK_DOC_RULE §1.5 표 / "큰 작업이면 폴더 승격"). 그러나 실사용에서 폴더 승격이 필요했던 적이 *한 번도 없음* — 추가 자료 다수 케이스가 희박. 자동 승격은 거의 안 쓰는 폴더 구조를 만들어 경로·일관성만 복잡하게.
- **요소**: 폴더 승격을 *모든 규모에서 기본 해제*. 규모 large 자동 트리거 제거. 오직 **사용자 명시 지시**일 때만 승격. 기본 = 항상 단일 파일 `NNN_slug.md`.
- **방법**:
  1. `task-init/SKILL.md` 폴더 승격 조건에서 **(a) 규모 large 제거** → "사용자 명시 시에만".
  2. `TASK_DOC_RULE.md` 표(§1.5)와 "큰 작업이면 폴더 승격" 문구를 *"사용자 명시 시 폴더 승격"*으로 정정.
  3. 폴더 승격 *기능 자체는 유지* — 자동 기본만 해제(사용자가 원하면 그대로 사용 가능).
- **얻는 것**: 거의 안 쓰는 폴더 구조 자동 생성 제거. large task도 단일 파일로 가볍게. 경로 일관성 단순.
- **주의**: closed-immutable hook은 단일·폴더 둘 다 이미 보호하므로 영향 없음. codex 미러(`template/.codex/`)도 같은 hook이라 문구 정합만 확인.
- **상태**: **적용 완료**(이번 버전). task-init Step 5 조건 + TASK_DOC_RULE §1.5 표·채번 문구 + README 스킬표를 *사용자 명시 한정*으로 정정. 폴더 승격 기능 자체는 유지.
- **출처**: 본 대화(2026-06-27) — 폴더 승격 자동 기본이 실사용에서 한 번도 필요 없었음. 명시 지시 한정으로 좁힘.
