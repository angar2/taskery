# taskery

taskery는 AI 코딩 에이전트에게 일을 맡길 때, 그 일을 **태스크** 단위로 열고, 진행하고, 마무리하게 해 주는 작업 체계입니다. Claude Code와 Codex에서 쓸 수 있습니다.

> **태스크** = 하나의 목적을 가진 작업 단위입니다. 버그 하나, 화면 하나, 기능 하나가 각각 태스크가 됩니다.

---

## taskery가 하는 일

taskery는 일을 둘로 나눕니다.

| 누가 | 무엇을 | 예 |
|---|---|---|
| **AI 에이전트** | 생각과 판단이 필요한 일 | 요구 정리, 코드 작성, 완료 기준 작성, 병합 충돌 해결 |
| **taskery 명령** | 누가 해도 결과가 같은 일 | 번호 붙이기, 브랜치·작업 폴더 만들기, 기록, 커밋, 병합, 정리 |

에이전트는 "이 단계에서 무엇을 판단하고 어떤 명령을 부를지"만 압니다. 실수하기 쉬운 반복 작업은 명령이 정확하게 처리합니다.

---

## 이런 문제를 해결합니다

| AI에게 그냥 맡기면 | taskery를 쓰면 |
|---|---|
| 무엇을 왜 바꿨는지가 긴 대화 속에 묻혀, 나중에 다시 찾기 어렵습니다 | 태스크마다 문서 한 장에 요구사항, 개발 계획, 완료 기준, 내린 결정, 실제 결과(테스트·커밋·병합)가 남습니다 |
| AI가 "완료했습니다"라고 하지만, 기능이 처음부터 끝까지 실제로 되는지는 아무도 해 보지 않았습니다 | 사용자가 화면에서 보게 될 결과로 완료 기준을 적고, 실제로 해 봅니다. 증거가 없으면 통과로 인정하지 않습니다 |
| 확인한다며 앱 화면을 띄우는 느린 테스트까지 매번 돌려 한참 기다립니다 | 개발 중에는 화면을 켜지 않는 코드 테스트만 돌리고, 3분을 넘으면 알려 줍니다 |
| AI가 어디까지 하고 멈출지 예측할 수 없습니다 | 사용자가 말한 데까지만 합니다. 말하지 않으면 한 단계만 하고 멈춥니다 |
| 여러 일을 동시에 맡기면 한 폴더에서 변경이 섞이고 병합이 엉킵니다 | 태스크마다 브랜치와 작업 폴더를 따로 만들고, 병합은 한 번에 하나씩 합니다 |
| 커밋 형식, 병합 방식, 브랜치 정리를 매번 다시 말해야 합니다 | 프로젝트의 git 규칙 표를 명령이 읽고 그대로 커밋·병합·정리합니다 |
| 프로젝트마다 다른 앱 실행 방법과 코딩 규칙을 매번 다시 설명합니다 | 프로젝트 전용 규칙 파일 두 장을 AI가 단계마다 읽습니다 |

## 일을 나누는 구조

taskery는 일을 세 층으로 나눕니다.

```
프로젝트 (리포 하나)
│
├─ 백로그 (BACKLOG.md)     떠오른 문제와 할 일을 모아 두는 곳 — 프로젝트에 하나
│
└─ 플랜
   └─ 001_mvp/
      ├─ PLAN.md            이 기능 묶음의 목표와 태스크 목록
      └─ tasks/             태스크 문서들 (TASK-001, TASK-002 …)
```

| 층 | 뜻 | 예 |
|---|---|---|
| 프로젝트 | taskery를 설치한 리포 하나 | 클립보드 관리 앱 |
| 플랜 | 기능 묶음 하나의 목표와 태스크 목록 | "고정 기능 강화" |
| 태스크 | 하나의 목적을 가진 작업 단위 | "고정한 항목을 사이드바에 보여 주기" |
| 백로그 | 아직 태스크가 되지 않은 문제와 할 일 | "백업 파일이 지워지지 않고 쌓인다" |

`PLAN.md`의 태스크 목록에는 먼저 끝나야 하는 항목(선행)을 함께 적습니다.

```markdown
## 태스크 목록
1. 로그인 화면 — 선행: 없음
2. 로그인 API 연결 — 선행: 1
```

taskery는 이 목록을 읽어 **지금 시작할 수 있는 태스크**를 알려 줍니다. 위 예에서는 1번이 끝나야 2번을 시작할 수 있습니다.

## 태스크가 진행되는 과정

모든 태스크는 다섯 단계를 거칩니다. 단계마다 AI가 읽는 짧은 안내서(**스킬**)가 하나씩 있고, 단계 끝에는 정해진 명령을 부릅니다.

```
① 시작 ──▶ ② 기획 ──▶ ③ 개발 ──▶ ④ 테스트 ──▶ ⑤ 마무리
```

| 단계 | AI가 하는 일 | 끝에 부르는 명령 | 명령이 하는 일 |
|---|---|---|---|
| ① 시작 | 요청이나 백로그 항목을 읽고, 태스크 하나로 묶을 범위·종류·크기·이름을 정합니다 | `prepare-task` | 겹치지 않는 번호를 발급하고, 전용 브랜치와 작업 폴더를 만들고, 태스크 문서를 만듭니다 |
| ② 기획 | 요구사항, 개발 계획, 완료 기준을 문서에 적고 사용자 확인을 받습니다 | `approve-plan` | 필요한 내용이 다 적혔는지 검사하고, 기획이 끝났다고 기록합니다 |
| ③ 개발 | 코드를 고치고 필요한 단위 테스트를 씁니다 | `test-code` | 등록된 코드 테스트를 돌리고, 통과한 순간의 코드 상태를 기록합니다 |
| ④ 테스트 | 앱을 한 번 켜서 완료 기준을 실제로 해 보고 증거를 남깁니다 | `test-scenario` | 완료 기준마다 결과와 증거를 기록합니다. 증거 없는 통과는 받지 않습니다 |
| ⑤ 마무리 | 태스크 중 내린 결정 가운데 앞으로도 지킬 것을 프로젝트 문서에 반영합니다 | `verify-close` → `commit-task` → `merge-task` → `close-task` | 검사하고, 커밋하고, 병합하고, 작업 폴더를 치운 뒤 걸린 시간을 보고합니다 |

마무리 명령 네 개는 각각 이런 일을 합니다.

| 명령 | 하는 일 |
|---|---|
| `verify-close` | 기획 확인이 있었는지, 코드 테스트 뒤에 코드가 바뀌지 않았는지, 모든 완료 기준에 결과와 증거가 있는지 검사합니다 |
| `commit-task` | 작업 묶음마다 커밋을 만들고, 병합 전에 볼 요약(커밋 목록, 바뀐 파일, 단계별 시간, 기획 뒤 늘어난 파일)을 보여 줍니다 |
| `merge-task` | 병합 잠금을 잡고, 그사이 들어온 다른 변경을 먼저 반영한 뒤 병합합니다. 충돌이 나면 멈추고, AI가 고친 뒤 다시 부르면 이어 갑니다 |
| `close-task` | 작업 폴더와 병합된 브랜치를 지우고, 태스크를 닫고, 백로그와 변경 기록을 갱신하고, 단계별 걸린 시간을 보고합니다 |

## 어디까지 하고 멈추는지

AI가 어디서 멈출지는 사용자의 말로 정해집니다.

| 사용자의 말 | AI의 동작 |
|---|---|
| (범위를 말하지 않음) | 한 단계만 하고 멈춰서 보고합니다 |
| "개발까지 해 줘" | 그 단계까지 멈추지 않고 이어 갑니다 |
| "끝까지 해 줘" | 병합과 정리까지 합니다. 기획 확인과 병합 확인도 맡긴 것으로 봅니다 |

범위와 상관없이 반드시 멈추는 곳은 세 군데뿐입니다.

1. 사용자가 눈으로 확인해야 하는 완료 기준이 있을 때
2. 테스트가 실패했을 때
3. AI가 풀지 못한 병합 충돌이 났을 때

강제 푸시처럼 되돌릴 수 없는 git 명령은 범위와 상관없이 언제나 사용자에게 먼저 묻습니다.

**대화 예시**

```
사용자: "설정 화면의 저장 버튼 색을 바꿔 줘"
  → 태스크를 열고 작업 폴더를 만든 뒤 멈춥니다 (범위를 말하지 않았으므로 한 단계)

사용자: "개발까지 해 줘"
  → 기획을 적고, 코드를 고치고, 코드 테스트를 통과시킨 뒤 멈춥니다

사용자: "끝까지 해 줘"
  → 완료 기준을 실제로 해 보고, 커밋·병합·정리까지 마칩니다
```

## 일의 크기에 맞추는 법 — 크기와 스위치

### 크기 — 문서에 얼마나 적을지

| | small | medium · large |
|---|---|---|
| 태스크 문서 | 요구사항, 개발 계획(고칠 파일), 완료 기준, 결정, 결과 | small과 같고, 개발 계획을 작업 묶음(Phase)으로 나눕니다 |
| 커밋 | 1개 | 작업 묶음마다 1개 |

크기는 AI가 제안합니다.

### 스위치 — 그 단계를 정식으로 거칠지

| 스위치 | 켜짐 (기본) | 꺼짐 |
|---|---|---|
| 기획 | 요구를 정리하고, 필요하면 되묻고, 기획 확인을 받습니다 | 요청 내용으로 짧게 적고 멈추지 않고 넘어갑니다 |
| 개발 | 코드를 고치고 코드 테스트를 합니다 | 코드를 바꾸지 않습니다. 점검만 하는 태스크에 씁니다 |
| 테스트 | 완료 기준을 실제로 해 봅니다 | 실제 확인 없이 마무리하거나 사용자에게 검수를 부탁합니다 |

- 기본은 모두 켜짐입니다. 사용자가 말했거나 요청에서 분명히 드러날 때만 AI가 한 줄로 묻고 바꿉니다.
- 개발과 테스트를 둘 다 끌 수는 없습니다. 할 일이 없는 태스크이기 때문입니다.

## 태스크 문서

태스크마다 마크다운 문서 한 장이 생깁니다.

```markdown
# TASK-012 설정 화면 저장 버튼 색 변경

| 생성일 | 플랜 | 유형 | 크기 | 스위치 | 범위 | 부모 브랜치 | 브랜치 | 상태 |
|---|---|---|---|---|---|---|---|---|
| 2026-10-04 | 001_mvp | improve | small | 기획·개발·테스트 | 끝까지 | dev | improve/claude_TASK-012_save-button-color | 닫힘(완료) |

| 시작·기획 | 개발 | 테스트 | 닫기 |
|---|---|---|---|
| ✅ 2분 | ✅ 3분 | ✅ 4분 | ✅ 1분 (합계 10분) |

## 요구사항
저장 버튼이 다른 버튼과 구분되지 않아 눈에 띄는 파란색으로 바꾼다.

- 사용자 요구: 저장 버튼이 바로 눈에 띄어야 한다.
- 하지 않는 것: 다른 버튼 색, 버튼 배치.

## 개발 계획
- `src/ui/SettingsView.tsx` — 저장 버튼 색을 디자인 토큰 primary로

## 테스트 계획
1. [AUTO] 설정 화면 → 저장 버튼을 본다 → 버튼이 파란색으로 보인다
2. [USER] 설정 화면 → 이름을 바꾸고 저장 → 목록에 바뀐 이름이 보인다

## 결정
- 파란색은 디자인 토큰 primary를 쓴다 — 다크 모드에서도 대비가 유지된다

## 결과
- 코드 테스트 · 통과 · 명령 2개 · 1분 · 2026-10-04 14:10
- 시나리오 1 · PASS · 캡처 screenshots/save-button.png · 2026-10-04 14:12
- 시나리오 2 · PASS · 사용자 확인 · 2026-10-04 14:14
- 커밋 · improve: [TASK-012] 설정 화면 저장 버튼 색 변경
- 병합 · dev ← e71b0a4 · 2026-10-04 14:15
```

| 부분 | 누가 쓰나 |
|---|---|
| 헤더 표(생성일, 플랜, 종류, 크기, 스위치, 범위, 부모 브랜치, 브랜치, 상태) | 명령 |
| 단계 표 | 명령 — 명령이 성공했을 때만 칸이 채워집니다 |
| 요구사항(첫 줄은 목표), 개발 계획, 테스트 계획, 결정 | AI |
| 결과(코드 테스트, 완료 기준 결과, 커밋, 병합) | 명령 |

- medium·large는 개발 계획을 작업 묶음(Phase)으로 나누고, 묶음마다 고칠 파일과 이유를 적습니다.
- 개발을 끈 태스크에는 개발 계획이, 테스트를 끈 태스크에는 테스트 계획이 없습니다.

단계 표는 AI의 "했습니다"가 아니라 **명령이 실제로 통과한 기록**입니다. 그래서 문서만 보면 태스크가 정말 어디까지 왔는지 알 수 있습니다. 태스크 상태는 열림과 닫힘(완료·포기)뿐이고, 손으로 바꾸는 상태는 없습니다.

## 테스트 방식

taskery는 테스트를 두 종류로 나눕니다.

| | 코드 테스트 | 실사용 테스트 |
|---|---|---|
| 언제 | 개발 단계 | 테스트 단계 |
| 무엇을 | 코드가 깨지지 않았는지 — 린트, 타입 검사, 빌드, 단위 테스트 | 사용자가 원한 일이 처음부터 끝까지 되는지 |
| 기준 | 앱 화면을 켜지 않는 것만 등록합니다. 3분을 넘으면 알려 줍니다(끊지는 않습니다) | 완료 기준 최대 5개 |
| 증거 | 명령 출력이 자동으로 기록됩니다 | 실행 출력, 화면 캡처 경로, 또는 사용자가 확인한 시각 |

### 완료 기준 쓰는 법

한 줄 형식은 `[AUTO 또는 USER] 시작 → 행동 → 기대하는 끝 상태`입니다.

- `[AUTO]`는 AI가 직접 해 보고 확인합니다.
- `[USER]`는 사용자가 눈으로 확인합니다. 디자인이 보기 좋은지 같은 것입니다.
- 한 줄에는 의도 하나, 한 번의 흐름만 담습니다.
- 기대하는 결과는 **사용자가 화면에서 보는 것**으로만 적습니다. "DB에 행이 생긴다" 같은 내부 값은 코드 테스트에서 확인합니다.
- 무언가를 없애는 태스크는 대신 무엇이 보여야 하는지를 함께 적습니다.

### 실사용 테스트에서 지키는 것

- 의도를 정면으로 해 봅니다. "빠져나갈 수 없다"가 목표라면 실제로 빠져나가 보고, 버튼이 회색인지만 보고 통과로 적지 않습니다.
- 앱은 한 번 켜서 완료 기준을 전부 확인합니다. 끌 때는 자기가 띄운 앱만 끕니다.
- 같은 결과가 두 번 연속 기대와 다르면 실패로 기록하고 멈춥니다. 원인 찾기는 개발 단계에서 합니다.
- "버튼이 눌리는가" 같은 부품 확인, 코드에 그 줄이 있는지 검색하는 확인, 요청하지 않은 화면 픽셀 비교는 하지 않습니다.
- 사용자가 실패를 알고도 마무리하자고 하면, 실패를 통과로 바꾸지 않고 "사용자가 알고 넘어갔다"는 기록을 그 말 그대로 남깁니다.

## 여러 태스크를 동시에

### 태스크마다 자기 작업 폴더

```
my-app/                             ← 본진 (리포 원래 폴더, dev 브랜치에 그대로)
~/.taskery/worktrees/…/TASK-012/    ← TASK-012 전용 작업 폴더 (전용 브랜치)
~/.taskery/worktrees/…/TASK-013/    ← TASK-013 전용 작업 폴더 (전용 브랜치)
```

- **작업 폴더(워크트리)** = git이 같은 리포를 다른 폴더에 하나 더 펼친 것입니다. 태스크마다 따로 있어 서로의 변경이 섞이지 않습니다.
- **본진** = 리포의 원래 폴더입니다. 끝난 태스크가 병합되어 들어오는 자리라서 그대로 둡니다.
- **부모 브랜치** = 본진이 서 있는 브랜치입니다. 태스크는 여기서 갈라져 나와 여기로 병합됩니다.
- 한 줄 수정도 작업 폴더를 만듭니다. 생략은 사용자가 직접 말할 때만 합니다.
- Orca(작업 폴더마다 AI 탭을 여는 터미널 앱) 안에서 쓰면 작업 폴더를 Orca가 만들고 탭으로 묶어 보여 줍니다.

### 동시에 돌려도 섞이지 않는 이유

| 걱정 | taskery의 처리 |
|---|---|
| 두 세션이 동시에 태스크를 열어 같은 번호를 받으면? | 번호를 잠금 안에서 발급하므로 겹치지 않습니다 |
| 두 태스크가 동시에 병합하면? | 병합 잠금이 있어 한 번에 하나씩 들어갑니다 |
| 먼저 병합된 변경과 충돌하면? | 명령이 멈추고, 그 태스크의 AI가 충돌 파일을 고친 뒤 다시 부르면 이어 갑니다 |
| 다른 태스크가 고친 용어집이 내 작업 폴더에는 없으면? | taskery 문서는 모든 작업 폴더가 본진의 한 벌을 함께 봅니다. 고치면 바로 공유됩니다 |

### 작업 폴더 준비 시간 줄이기

새 작업 폴더에서 처음부터 빌드하면 오래 걸립니다. taskery는 다음 방법으로 이 시간을 줄입니다.

1. 설치할 때 프로젝트를 보고 빌드 결과 폴더(Rust `target`, Xcode `DerivedData`)를 등록합니다.
2. 새 작업 폴더를 만들 때 본진의 빌드 결과 폴더를 **APFS 복제**로 심습니다. APFS 복제는 macOS가 파일을 실제로 복사하지 않고 1초 만에 복사본처럼 보이게 만드는 기능입니다. 바뀐 부분만 디스크를 씁니다.
3. 각 작업 폴더는 자기 복사본으로 이어서 빌드하므로 처음부터 빌드하지 않습니다.
4. 태스크가 끝나 닫힐 때 그 빌드 결과를 본진으로 다시 복제해, 다음 태스크의 출발점으로 씁니다.

Node 프로젝트는 `package-lock.json`이 있으면 `npm ci`로 설치합니다. macOS가 아니면 복제를 건너뛰고 평소처럼 빌드합니다.

## 오케스트레이션 — 한 줄 지시로 여러 태스크를 나눠 맡기기

**오케스트레이션** = 한 세션(관리 세션)이 백로그를 태스크로 나누고, 태스크마다 새 AI 탭을 띄워 맡기고, 보고를 받아 정리하는 방식입니다. Orca 안에서 씁니다.

```
                          👤 사용자
          ① 한 줄 지시 ↙               ↘ ⑥ 확인은 그 탭에서 직접 답
┌─ 🏠 본진 ───────────────┐          ┌─ 🪟 Orca ──────────────────┐
│ 🎛 관리 세션             │ ③ ─────▶ │ TASK-107 탭  📁 + 🧠 Claude │
│   ↑ ② 읽고 나눔          │ ─────▶   │ TASK-108 탭  📁 + 🧠 Codex  │
│ 📥 BACKLOG   🗂 PLAN    │ ─────▶   │ TASK-109 탭  📁 + 🧠 Claude │
│ 📬 보고함  ◀───── ④ 한 줄 보고 ──── │                             │
│   ⑤ 보고가 오면 깨어남    │          │                             │
│ 🌿 dev  ◀──── ⑦ 하나씩 병합 ────── │                             │
└─────────────────────────┘          └─────────────────────────────┘
```

| 순서 | 무슨 일이 일어나나 |
|---|---|
| ① | 사용자가 관리 세션에 한 줄로 지시합니다. 예: "백로그 BL-1~3을 끝까지 진행해" |
| ② | 관리 세션이 백로그와 `PLAN.md`를 읽고 태스크로 나눕니다. 어떤 태스크를 어떤 순서와 AI로 진행할지 표로 보여 주고 확인받습니다. 지시에 이미 정해져 있으면 다시 묻지 않습니다 |
| ③ | 태스크마다 작업 폴더를 만들고(`prepare-task`), Orca 새 탭에 Claude나 Codex를 띄워 첫 지시를 보냅니다(`orca-dispatch-task`) |
| ④ | 각 탭이 자기 작업 폴더에서 기획부터 마무리까지 진행합니다. 끝났을 때, 확인을 기다릴 때, 질문이 있을 때, 막혔을 때 보고함에 한 줄 남깁니다(`report-task`) |
| ⑤ | 관리 세션은 기다리는 동안 잠들어 있어 토큰을 쓰지 않습니다(`wait-reports`). 보고가 오거나 10분이 지나면 깨어나 처리합니다 |
| ⑥ | 사용자 확인이 필요하면 관리 세션이 "TASK-108 탭에서 화면 확인해 주세요"라고 알립니다. 사용자는 그 탭에서 직접 답합니다 |
| ⑦ | 끝난 태스크는 병합 잠금 안에서 하나씩 dev에 병합됩니다(`merge-task`) |
| ⑧ | 관리 세션이 끝난 태스크의 작업 폴더와 탭을 치우고(`close-task`), 시작할 수 있는 다음 태스크로 빈자리를 채웁니다. 그리고 ③으로 돌아갑니다 |

- **왜 서브에이전트가 아니라 탭인가요?** 서브에이전트는 맡긴 쪽과 주고받는 대화가 없고, 사용자가 중간에 들여다보거나 끼어들 수 없습니다. 탭으로 띄운 세션은 사용자가 언제든 열어 보고 직접 말할 수 있습니다.
- **승인은 사용자만 합니다.** 관리 세션이 탭에 보내는 말은 `[오케스트레이션]`으로 시작하고, 태스크 세션은 이 말을 승인으로 받아들이지 않습니다.
- **순서를 지킵니다.** 선행 태스크가 끝나지 않은 태스크는 열지 않습니다. 같은 파일을 크게 고치는 태스크끼리는 차례로 진행합니다.

## 백로그

떠오른 문제와 할 일은 `.taskery/BACKLOG.md` 한 곳에 모읍니다.

```markdown
### BL-3 [feature] 클립보드 확인 주기(500ms) 설정 노출
- 상태: 대기
- 등록: 2026-10-01
- 현상: 확인 주기가 500ms로 고정돼 있어 사용자가 바꿀 수 없다.
- 연결 태스크: –
```

```
대기 ──(태스크로 옮김)──▶ 진행 ──(연결된 태스크가 끝나 닫힘)──▶ 완료 ("끝난 항목"으로 이동)
                             └──(연결된 태스크를 모두 포기)──▶ 대기로 돌아감
```

- `add-backlog` 스킬이 번호를 받아 종류, 제목, 현상을 채웁니다. 우선순위 같은 선택 칸은 근거가 있을 때만 적고, 지어내서 채우지 않습니다.
- 상태는 명령이 바꿉니다. 사람이 직접 적는 상태는 `보류`와 `취소`뿐입니다.

## 쓰는 방식 다섯 가지

상황에 맞게 섞어 쓰면 됩니다.

| 방식 | 모습 | 이렇게 말합니다 |
|---|---|---|
| 한 단계씩 | 단계마다 결과를 보고 다음을 지시합니다 | "로그인 버튼 색 바꿔 줘" → "다음" → "다음" |
| 범위 맡기기 | 어디까지 할지 정해 맡깁니다 | "개발까지 해 줘", "끝까지 해 줘" |
| 백로그 | 의논하며 할 일을 쌓아 두고, 나중에 꺼내 태스크로 엽니다 | "이거 백로그에 적어 둬" → "BL-3 태스크로 열어서 끝까지 해 줘" |
| 병렬 | 세션 여러 개를 열어 각자 다른 태스크를 진행합니다 | 세션마다 "BL-1 끝까지", "BL-2 끝까지" |
| 오케스트레이션 | 한 세션이 여러 태스크를 새 탭에 나눠 맡깁니다 | "BL-1~3을 오케스트레이션으로 끝까지 진행해" |

## 빠른 시작

> **준비물**: Node.js 18 이상, git 2.31 이상, 위 두 에이전트 중 하나 이상. 오케스트레이션을 쓰려면 Orca가 필요합니다.

### 1. 설치

```bash
# 새 프로젝트 — 폴더를 만들고 그 안에 설치합니다
npx -p @angar2/taskery create-taskery my-app

# 기존 프로젝트 — 리포 루트에서 설치합니다 (어떤 에이전트를 쓸지 묻습니다)
cd my-app
npx @angar2/taskery init

# 다른 에이전트를 추가합니다
npx @angar2/taskery add codex

# 새 버전이 나오면 갱신합니다
npx @angar2/taskery update
```

- 빈 폴더에서 `init`을 부르면 git 시작, 빈 첫 커밋, 통합 브랜치(기본 `dev`) 만들기까지 한 번에 합니다.
- 파일은 있는데 git이나 첫 커밋이 없는 폴더에서는 멈춥니다. 첫 커밋에 무엇을 넣을지(예: `.env` 같은 비밀값을 넣을지)는 사용자가 정할 일이기 때문입니다. 첫 커밋을 직접 만든 뒤 다시 부르면 됩니다.
- 전역으로 설치하면(`npm install -g @angar2/taskery`) `npx @angar2/taskery` 대신 `taskery`로 부를 수 있습니다.

### 2. 프로젝트 소개하기

AI 세션을 열고 `project-init` 스킬을 부릅니다(예: `/project-init`). 기획 문서가 있으면 그것을 읽고, 없으면 무엇을 만드는지, 누가 쓰는지, 핵심 기능과 기술 스택이 무엇인지 짧게 묻습니다. 그러면 다음이 만들어집니다.

- 프로젝트 소개, 용어집, 필요한 제품 문서
- 코드 테스트 명령 등록
- 프로젝트 전용 규칙(앱 실행 방법, 구현 규칙)
- 첫 플랜과 태스크 목록

### 3. 첫 태스크

```
사용자: "설정 화면에 다크 모드 토글을 추가해 줘. 끝까지 해 줘."
```

AI가 태스크를 열고 기획, 개발, 테스트, 마무리까지 진행합니다. 끝나면 무엇을 바꿨는지와 단계별 걸린 시간을 보고합니다. 진행 중에는 언제든 `npx @angar2/taskery status`로 열린 태스크와 진행 상황을 볼 수 있습니다.

## 설치되는 것

```
my-app/
├─ AGENTS.md                 AI가 세션마다 읽는 짧은 지침 (약 15줄)
├─ CLAUDE.md                 AGENTS.md를 불러오는 한 줄
├─ .mcp.json                 AI가 taskery 명령을 도구로 부르게 하는 연결 설정
├─ .claude/                  스킬 10장과 설정
├─ .codex/                   스킬 10장과 도구 연결 (Codex를 고른 경우)
└─ .taskery/
   ├─ manifest.json          설치 정보, 코드 테스트 명령, 빌드 결과 폴더 등록
   ├─ rules/                 규칙 문서 7장
   ├─ BACKLOG.md             백로그
   └─ (쓰면서 생기는 것)     PROJECT.md · GLOSSARY.md · spec/ · plans/ · changelog/ …
```

### 모두 git 밖에 둡니다

taskery 파일은 그 리포에만 적용되는 git 무시 목록(`.git/info/exclude`)에 들어가 git이 추적하지 않습니다. `.gitignore`는 건드리지 않습니다.

- 설치해도 리포의 추적 파일이 하나도 바뀌지 않습니다. 커밋되는 것은 코드뿐입니다.
- 모든 작업 폴더가 본진의 taskery 문서 한 벌을 함께 봅니다. 한 태스크가 고친 용어집을 다른 태스크가 곧바로 봅니다.
- 그 대신 태스크 문서와 백로그는 git 이력에 남지 않습니다. 다른 사람과 git으로 공유해야 하는 문서는 `.taskery/` 밖(예: `docs/`)에 두면 됩니다.
- git이 이미 이 파일들 중 하나를 추적하고 있으면 `init`은 설치를 멈추고 어떤 파일인지 알려 줍니다. 추적 해제는 리포 이력을 바꾸는 일이라 사용자가 직접 합니다.

### 규칙 문서 7장

| 문서 | 내용 | 갱신 |
|---|---|---|
| `TASKERY_RULE.md` | taskery 참고서 — 막혔을 때만 읽습니다 | `update`가 새 버전으로 바꿉니다 |
| `GIT_RULE.md` | 이 리포의 git 규칙. 맨 위 표(통합 브랜치, 브랜치 이름, 커밋 메시지, 병합 방식)를 명령이 읽어 따릅니다 | `update`가 바꿉니다(고쳤으면 먼저 묻습니다) |
| `TASK_DOC_RULE.md` | 태스크 문서 쓰는 법 | `update`가 바꿉니다 |
| `CHANGELOG_RULE.md` | 변경 기록 형식 | `update`가 바꿉니다 |
| `MOCKUP_RULE.md` | 화면 목업의 위치와 형식 — 목업을 요청했을 때만 씁니다 | `update`가 바꿉니다 |
| `TEST_RULE.local.md` | **이 프로젝트의** 앱 실행 방법과 실사용 테스트 방식 | 프로젝트 소유 — `update`가 건드리지 않습니다 |
| `DEV_RULE.local.md` | **이 프로젝트의** 구현 규칙 | 프로젝트 소유 — `update`가 건드리지 않습니다 |

## 스킬

**스킬** = AI가 어느 단계에서 무엇을 판단하고 어떤 명령을 부를지 알려 주는 짧은 안내서입니다. 이름으로 직접 부르거나(예: `/task-init`), 요청 내용이 맞으면 AI가 스스로 고릅니다.

| 스킬 | 쓰는 때 | 하는 일 |
|---|---|---|
| `project-init` | 처음 한 번 | 프로젝트 정보, 용어집, 제품 문서, 코드 테스트 등록, 프로젝트 전용 규칙, 첫 플랜을 만듭니다 |
| `plan-init` | 새 기능 묶음을 시작할 때 | 플랜 폴더와 `PLAN.md`(목표, 선행 관계가 있는 태스크 목록)를 만듭니다 |
| `task-init` | 태스크를 열 때 | 요청이나 백로그 항목을 태스크 하나로 정리해 엽니다 |
| `task-plan` | 기획 단계 | 요구사항, 개발 계획, 완료 기준을 적습니다 |
| `task-dev` | 개발 단계 | 구현하고 코드 테스트를 통과시킵니다 |
| `task-test` | 테스트 단계 | 완료 기준을 실제로 해 보고 증거를 남깁니다 |
| `task-close` | 마무리 단계 | 검사, 커밋, 병합을 하고, 태스크를 연 쪽이 작업 폴더를 정리합니다 |
| `task-orche` | 여러 태스크를 나눠 맡길 때 | 백로그를 태스크로 나누고, 새 탭에 맡기고, 보고를 받아 정리합니다 |
| `add-backlog` | 할 일을 적어 둘 때 | 백로그에 항목 하나를 등록합니다 |
| `log-friction` | taskery가 불편할 때 | 사용자가 겪은 불편을 `.taskery/FRICTION_LOG.md`에 한 줄로 남깁니다(사용자가 원할 때만) |

## 명령

명령은 AI가 스킬을 따라 부릅니다. 사용자가 직접 부를 일은 주로 설치 명령과 `status`입니다. AI는 명령을 도구(MCP — AI가 외부 도구를 직접 부르는 연결 방식)로 부르고, 도구가 없으면 `npx @angar2/taskery <명령>`으로 부릅니다.

| 명령 | 하는 일 |
|---|---|
| `status` | 열린 태스크, 단계 표, 단계별 시간, 문서와 작업 폴더 경로, 플랜별로 지금 시작할 수 있는 태스크를 보여 줍니다 |
| `plan-init <이름>` | 다음 번호로 플랜 폴더와 `PLAN.md` 틀을 만듭니다 |
| `prepare-task "<제목>" --slug --type --size …` | 태스크를 엽니다 — 번호, 브랜치, 작업 폴더, 태스크 문서, 백로그 연결 |
| `approve-plan <TASK>` | 태스크 문서를 검사하고 기획 끝을 기록합니다 |
| `test-code [TASK]` | 등록된 코드 테스트를 돌립니다. `--register "<명령>"`으로 테스트 명령을 등록합니다 |
| `test-scenario <TASK> <번호> pass\|fail "증거"` | 완료 기준의 결과를 기록합니다. 사용자가 실패를 알고 넘어가기로 하면 `accept "<사용자가 한 말>"`로 남깁니다 |
| `verify-close <TASK>` | 마무리 전 검사를 합니다 |
| `commit-task <TASK>` | 작업 묶음별로 커밋하고 병합 전 요약을 보여 줍니다 |
| `merge-task <TASK>` | 잠금 안에서 최신 변경을 반영하고 병합합니다. 충돌 뒤 다시 부르면 이어 갑니다 |
| `close-task <TASK>` | 작업 폴더와 브랜치를 정리하고, 태스크를 닫고, 백로그와 변경 기록을 갱신하고, 걸린 시간을 보고합니다 |
| `prune` | 닫힌 태스크에 남은 작업 폴더와 브랜치를 정리합니다(항목마다 묻습니다) |
| `backlog-add` · `backlog-get` · `backlog-mark` | 백로그 항목을 만들고, 읽고, 태스크에 연결합니다 |
| `orca-dispatch-task` · `report-task` · `wait-reports` | 오케스트레이션용 — 탭 띄우기, 보고 남기기, 보고 기다리기 |
| `init` · `update` · `add <claude\|codex>` | 설치, 갱신, 에이전트 추가 |

전체 옵션은 `npx @angar2/taskery help`로 볼 수 있습니다. 명령이 멈출 때는 왜 멈췄는지와 다음에 무엇을 하면 되는지를 함께 알려 줍니다.

## 실제로 돌려 본 결과

실제 앱 프로젝트 두 개의 복사본으로 시험했습니다. 하나는 macOS 클립보드 앱(Swift, Xcode, 코드 테스트 600여 개)이고, 하나는 데스크톱 앱(Rust·Tauri와 Node)입니다.

| 시험 | 결과 |
|---|---|
| 작은 태스크 하나를 "끝까지" | 요청부터 닫기까지 약 10분 걸렸습니다. 태스크 열기 28초, 기획 2분, 개발과 실사용 테스트 6분 30초, 마무리 1분 30초입니다 |
| 작업 폴더 준비(Swift 앱) | 요청부터 준비 완료까지 약 38초 걸렸습니다. 1.1GB 빌드 결과를 복제하는 데 4초가 들었습니다 |
| 작업 폴더 준비(Rust 앱) | 6.7초 걸렸습니다. 그 폴더에서 빌드하는 데 26.8초가 걸렸습니다. 처음부터 빌드하면 130초입니다 |
| 두 태스크 동시 진행 | 번호가 겹친 일은 없었습니다. 병합 충돌 1건은 명령이 멈추고 AI가 고친 뒤 이어 갔습니다 |
| 오케스트레이션으로 백로그 3건 "끝까지" | 관리 세션에 한 줄로 지시하자 1분 안에 탭 3개가 배분됐습니다. 2건은 12분, 17분 만에 병합됐고(서로 충돌한 부분도 스스로 해결), 1건은 사용자 화면 확인에서 멈췄다가 확인 뒤 병합됐습니다. 사용자 확인을 기다린 16분을 포함해 모두 35분 걸렸습니다 |
| 끝난 뒤 남은 것 | 작업 폴더, 브랜치, 탭, 테스트 앱 모두 0개였습니다 |

## 하지 않는 것

- PR로 병합하는 방식은 다루지 않습니다. 병합은 로컬에서만 합니다.
- 태스크 문서와 백로그는 git 이력에 남지 않습니다.
- 빌드 결과 복제는 macOS에서만 됩니다. 다른 환경에서는 평소처럼 빌드합니다.
- 오케스트레이션은 Orca 안에서만 됩니다.
- Codex는 작업 폴더로 옮겨 갈 수 없습니다. Codex로 태스크를 하려면 오케스트레이션이 Codex 탭을 띄우거나, 사용자가 그 작업 폴더에서 Codex를 엽니다.

## 자주 묻는 질문

**한 줄만 고치는 일도 태스크를 열어야 하나요?**
네. 한 줄 수정도 브랜치와 작업 폴더를 만들어야 동시에 다른 태스크가 돌아가도 섞이지 않습니다. 대신 크기를 small로 하고 스위치로 단계를 줄일 수 있습니다. 작업 폴더를 꼭 생략하고 싶으면 그렇게 말하면 됩니다.

**AI가 "통과했다"고 잘못 말하면 어떻게 되나요?**
통과에는 증거가 필요합니다. 마무리 검사는 모든 완료 기준에 결과와 증거가 있는지, 코드 테스트 뒤에 코드가 바뀌지 않았는지를 확인합니다. 단계 표도 명령이 성공했을 때만 채워집니다.

**taskery가 강제로 막는 것은 무엇인가요?**
네 가지뿐입니다. 번호가 겹치는 것, 두 태스크가 동시에 병합되는 것, 증거 없이 마무리하는 것, 개발도 테스트도 하지 않는 태스크를 여는 것입니다. 나머지는 AI의 판단에 맡깁니다.

**걸린 시간은 어떻게 알 수 있나요?**
명령마다 시각을 기록해 두었다가, 태스크를 닫을 때 단계별 시간과 합계를 보고합니다. 일하는 중인 AI에게는 시간 목표를 보여 주지 않습니다. 재촉받은 AI는 확인을 건너뛰기 쉽기 때문입니다.

**두 에이전트를 섞어 써도 되나요?**
됩니다. 설치할 때 둘 다 고르거나 나중에 `npx @angar2/taskery add codex`로 추가합니다. 오케스트레이션에서는 태스크마다 다른 에이전트와 모델을 맡길 수 있습니다.

**우리 프로젝트만의 앱 실행 방법이나 코딩 규칙은 어디에 적나요?**
`.taskery/rules/TEST_RULE.local.md`(앱 실행과 테스트 방식)와 `DEV_RULE.local.md`(구현 규칙)에 적습니다. 업데이트가 덮어쓰지 않는 프로젝트 전용 파일입니다. 일하다 새 규칙이 필요해지면 AI가 문장을 제안하고, 사용자가 승인하면 들어갑니다.

**taskery를 쓰다 불편한 점이 있으면요?**
`log-friction` 스킬로 그 불편을 한 줄 기록해 둡니다. 사용자가 실제로 겪은 불편만 적습니다.

## 0.8.x에서 옮겨 오는 경우

1.0은 0.8.x와 호환되지 않으며, 자동으로 옮겨 주는 기능도 없습니다.

1. 옛 taskery 파일(`AGENTS.md`·`CLAUDE.md`·`.claude/`·`.codex/`·`.agents/`·`.project/`·`.mcp.json`·`.taskery-manifest.json`)을 리포 밖으로 옮깁니다. git이 추적하고 있었다면 추적을 해제해 커밋합니다.
2. `npx @angar2/taskery init`으로 새로 설치합니다.
3. 필요한 옛 백로그와 제품 문서는 옮겨 둔 곳에서 새 `.taskery/`로 직접 가져옵니다.

0.x로 설치된 리포에서 `update`를 부르면 아무 파일도 바꾸지 않고 이 절차를 알려 준 뒤 멈춥니다.
