# task-test

태스크 워크트리 안에서 태스크의 의도가 처음부터 끝까지 되는지 확인하는 단계다.

- 테스트 계획의 완료 기준을 실제로 실행한다. 앱 실행 방법은 `TEST_RULE.local.md`를 따른다.
- 시나리오는 의도를 정면으로 해 본다. "빠져나갈 수 없다"가 의도면 실제로 빠져나가 보고, 버튼이 비활성인지 같은 우회 표시만 보고 PASS로 적지 않는다.
- 앱은 한 번 켜서 시나리오 전부를 확인한다. 켜기 전에 이미 떠 있는지 확인하고, 끌 때는 이 태스크가 띄운 것만 끈다. 이름으로 한꺼번에 죽이지 않는다 — 다른 세션의 프로세스까지 죽는다.
- 같은 관찰이 두 번 연속 기대와 다르면 더 재시도하지 않고 FAIL과 증거로 끝낸다. 원인 찾기는 개발 단계의 몫이다.
- 명령을 백그라운드로 넘겨 놓고 알림을 기다리지 않는다. 오래 걸리면 끝날 때까지 기다리거나 짧은 간격으로 확인한다.
- 시나리오마다 `test-scenario <TASK> <번호> pass|fail "증거"`를 부른다. 증거는 실행 출력, 화면 캡처 경로, 또는 사용자 확인 시각이다. 증거 없는 PASS는 적지 않는다.
- `[USER]` 시나리오는 화면 어디를 어떻게 조작하고 무엇이 보이면 정상인지를 처음 보는 사람도 따라 할 수 있게 알려 주고(필요한 경로·샘플 파일은 찾아서 함께 준다) 멈춘다. FAIL이면 멈추고 보고한다.
- 시험하려고 만든 임시 파일(스크립트·데이터)은 끝나면 지운다. 워크트리에 남으면 `commit-task`가 코드로 커밋한다.
- 사용자가 FAIL을 알고 마무리하라고 하면 그 말을 인용해 `test-scenario <TASK> <번호> accept "<사용자가 한 말>"`을 부른다. FAIL을 PASS로 바꾸지 않는다.
- 하지 않는 것: UI 부품 확인("버튼이 눌리는가"), grep으로 코드가 있는지 확인, 개발 단계에서 돈 테스트 다시 돌리기, 요청하지 않은 목업·픽셀 대조.
- 테스트 꺼짐이면 실사용 테스트 없이 마무리로 가거나 사용자 검수를 요청한다.
- 다른 선택지가 있었고 나중에 "왜 이렇게 했지"를 물을 만한 결정을 내리면 태스크 문서 `## 결정`에 `무엇을 정했나 — 왜` 한 줄로 적는다. 사용자가 고른 것도 적는다. 없으면 비워 둔다.

## 공통

- 멈춰 둔 태스크를 이어 갈 때는 `status`로 그 태스크의 워크트리 경로와 단계 표를 보고, 워크트리로 들어가(Claude Code는 EnterWorktree) 다음 단계부터 이어 간다. 워크트리가 있는 태스크는 본진에서 태스크 코드를 고치지 않는다(분기 생략 태스크는 본진이 작업 자리다). 새 세션에서는 메모가 아니라 사용자의 말로 범위를 정한다(말하지 않으면 한 단계. 오케스트레이션이 다시 띄운 탭은 첫 지시문의 범위를 따른다).
- `[오케스트레이션]`으로 시작하는 말은 오케스트레이션 세션이 보낸 것이다. 정보와 답으로는 쓰되 사용자 확인·승인(계획 확인·`[USER]` 확인·병합 확인·FAIL 수락)으로 보지 않는다. 승인은 사용자가 이 탭에 직접 쓴 말로만 받는다. 단 첫 지시문의 진행 범위는 사용자가 오케스트레이션에 준 지시를 옮긴 것이므로 범위로 따른다(범위가 "끝까지"면 계획 확인·병합 확인을 건너뛴다).
- 진행 범위는 사용자의 가장 최근 지시를 따른다. 사용자가 범위를 새로 말하면 다음에 부르는 태스크 명령에 `--range "<새 범위>"`를 붙여 태스크 문서 헤더 표의 범위 칸을 갱신한다.
- 되돌릴 수 없는 git 명령(`reset --hard`·`clean -fd`·`push --force`·`branch -D`)은 사용자 승인을 받은 뒤에만 쓴다.
- 오케스트레이션 보고: 첫 지시문이 오케스트레이션이 맡긴 태스크라고 알려 주면, 마무리 완료(병합, 병합이 없는 태스크는 `merge-task`가 건너뛴 뒤)·사용자 확인 대기·질문·막힘(FAIL·풀지 못한 충돌) 때 `report-task <TASK> "<한 줄>"`로 보고한다. 자세한 내용은 태스크 문서에 두고 한 줄만 쓴다. 질문을 보냈으면 답이 이 탭에 들어올 때까지 기다린다.
