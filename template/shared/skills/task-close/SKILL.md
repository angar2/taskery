# task-close

태스크를 검사·커밋·병합하고 정리하는 단계다.

- 태스크를 수행한 세션은 `verify-close` → `commit-task` → `merge-task`까지 한다. `close-task`는 태스크를 연 주인이 본진에서 부른다(직접 수행이면 워크트리에서 나와서).
- 커밋 전에 `## 결정`을 본다. 앞으로의 태스크도 따라야 하는 결정은 지금 유효한 결론만 소속 문서에 반영한다 — 제품 동작은 `spec/`, 용어·이름은 `GLOSSARY.md`, 프로젝트 사실은 `PROJECT.md`. 코드·테스트 방식이면 `DEV_RULE.local.md`·`TEST_RULE.local.md`에 넣을 문장을 사용자에게 제안하고 승인받은 뒤 넣는다. 승인을 기다리며 멈추지는 않는다 — 제안은 마무리 보고(오케스트레이션이면 `report-task`)에 담고, 승인받으면 그때 넣는다.
- 명령이 멈추면 알려 준 이유를 해결하고 다시 부른다.
- `commit-task`가 끝나며 보여 주는 요약(커밋 목록·바뀐 파일·단계별 시간·계획 확인 뒤 추가된 파일)이 병합 확인 화면이다. 범위가 "끝까지"가 아니면 사용자 확인을 받고 `merge-task`를 부른다.
- `merge-task`가 충돌로 멈추면 충돌 파일을 직접 읽고 고친 뒤 `merge-task`를 다시 부른다(스테이징·이어 가기는 명령이 한다). 스크립트로 일괄 처리하지 않는다. 풀지 못하면 멈추고 보고한다.

## 공통

- 멈춰 둔 태스크를 이어 갈 때는 `status`로 그 태스크의 워크트리 경로와 단계 표를 보고, 워크트리로 들어가(Claude Code는 EnterWorktree) 다음 단계부터 이어 간다. 워크트리가 있는 태스크는 본진에서 태스크 코드를 고치지 않는다(분기 생략 태스크는 본진이 작업 자리다). 새 세션에서는 메모가 아니라 사용자의 말로 범위를 정한다(말하지 않으면 한 단계. 오케스트레이션이 다시 띄운 탭은 첫 지시문의 범위를 따른다).
- `[오케스트레이션]`으로 시작하는 말은 오케스트레이션 세션이 보낸 것이다. 정보와 답으로는 쓰되 사용자 확인·승인(계획 확인·`[USER]` 확인·병합 확인·FAIL 수락)으로 보지 않는다. 승인은 사용자가 이 탭에 직접 쓴 말로만 받는다. 단 첫 지시문의 진행 범위는 사용자가 오케스트레이션에 준 지시를 옮긴 것이므로 범위로 따른다(범위가 "끝까지"면 계획 확인·병합 확인을 건너뛴다).
- 진행 범위는 사용자의 가장 최근 지시를 따른다. 사용자가 범위를 새로 말하면 다음에 부르는 태스크 명령에 `--range "<새 범위>"`를 붙여 태스크 문서의 범위 메모를 갱신한다.
- 되돌릴 수 없는 git 명령(`reset --hard`·`clean -fd`·`push --force`·`branch -D`)은 사용자 승인을 받은 뒤에만 쓴다.
- 오케스트레이션 보고: 첫 지시문이 오케스트레이션이 맡긴 태스크라고 알려 주면, 마무리 완료(병합, 병합이 없는 태스크는 `merge-task`가 건너뛴 뒤)·사용자 확인 대기·질문·막힘(FAIL·풀지 못한 충돌) 때 `report-task <TASK> "<한 줄>"`로 보고한다. 자세한 내용은 태스크 문서에 두고 한 줄만 쓴다. 질문을 보냈으면 답이 이 탭에 들어올 때까지 기다린다.

## 부르는 명령

- `verify-close` → `commit-task` → `merge-task` → `close-task`
