# TASK_DOC_RULE

> 태스크 문서를 쓰는 법이다. `task-plan`이 헷갈릴 때 읽는다.

## 1. 모양

`prepare-task`가 `.taskery/plans/<플랜>/tasks/<NNN>_<slug>.md`를 만든다.

```markdown
# TASK-012 설정 화면 저장 버튼 색 변경

| 생성일 | 플랜 | 유형 | 크기 | 스위치 | 범위 | 부모 브랜치 | 브랜치 | 상태 |
|---|---|---|---|---|---|---|---|---|
| 2026-10-04 | 001_mvp (항목 3) | improve | small | 기획·개발·테스트 | 끝까지 | dev | improve/claude_TASK-012_save-button-color | 열림 |

| 시작·기획 | 개발 | 테스트 | 닫기 |
|---|---|---|---|
| ✅ 2분 | ✅ 3분 | ⏳ | – |

## 요구사항
저장 버튼이 다른 버튼과 구분되지 않아 눈에 띄는 파란색으로 바꾼다.

- 사용자 요구: 저장 버튼이 바로 눈에 띄어야 한다.
- 다크 모드에서도 구분돼야 한다.
- 하지 않는 것: 다른 버튼 색, 버튼 배치.

## 개발 계획
- `src/ui/SettingsView.tsx` — 저장 버튼 색을 디자인 토큰 primary로

## 테스트 계획
1. [AUTO] 설정 화면 → 저장 버튼을 본다 → 버튼이 파란색으로 보인다

## 결정
- 파란색은 디자인 토큰 primary를 쓴다 — 다크 모드에서도 대비가 유지된다

## 결과
- 코드 테스트 · 통과 · 명령 2개 · 1분 · 2026-10-04 14:10
- 시나리오 1 · PASS · 캡처 screenshots/save-button.png · 2026-10-04 14:20
- 커밋 · improve: [TASK-012] 설정 화면 저장 버튼 색 변경
- 병합 · dev ← e71b0a4 · 2026-10-04 14:25
```

- **헤더 표와 단계 표는 명령이 쓴다.** 손대지 않는다. 범위가 바뀌면 다음 태스크 명령에 `--range "<새 범위>"`를 붙인다.
- 상태는 `열림`·`닫힘(완료)`·`닫힘(포기)` 셋이다. 분기 없이 일하는 태스크는 브랜치 칸이 `분기 없음`이다.
- 개발이 꺼진 태스크에는 `## 개발 계획`이, 테스트가 꺼진 태스크에는 `## 테스트 계획`이 없다.
- 짧게 쓰되 절마다 아래 2절의 내용은 빠뜨리지 않는다.

## 2. 절마다 쓰는 법

| 절 | 쓰는 법 |
|---|---|
| `## 요구사항` | **첫 줄은 목표** — 무엇을 왜 하는지 한 문장, 목록 기호 없이. 이 줄이 small 커밋의 사유와 변경 기록 요약이 된다. 그 아래 목록으로 사용자 요구, 정한 범위, 한계, 하지 않는 것을 적는다 |
| `## 개발 계획` | small은 한 줄에 `- 경로 — 무엇을` 하나. 폴더는 `src/auth/`처럼 끝에 `/`. medium·large는 아래 4절의 Phase |
| `## 테스트 계획` | 완료 기준(실사용 테스트 시나리오). 아래 3절 |
| `## 결정` | 다른 선택지가 있었고 나중에 "왜 이렇게 했지"를 물을 만한 결정만 `무엇을 정했나 — 왜` 한 줄로 적는다. 사용자가 고른 것도 적는다. 없으면 비운다 |
| `## 결과` | `test-code`·`test-scenario`·`commit-task`·`merge-task`가 한 줄씩 붙인다. 직접 쓰지 않는다 |

`approve-plan`은 요구사항 첫 줄(목표)이 있는지, 개발이 켜져 있으면 개발 계획에 파일이 있는지, 테스트가 켜져 있으면 완료 기준이 1~5개인지 본다.

## 3. 완료 기준

```markdown
## 테스트 계획
1. [AUTO] 설정 화면 → 저장 버튼을 본다 → 버튼이 파란색으로 보인다
2. [USER] 설정 화면 → 이름을 바꾸고 저장 → 목록에 바뀐 이름이 보인다
```

- 한 줄 형식은 `<번호>. [AUTO|USER] 시작 → 행동 → 기대하는 끝 상태`, 최대 5개. `test-scenario`의 번호는 이 순서다.
- `[AUTO]`는 AI가 실행해 확인하고, `[USER]`는 사용자가 눈으로 확인한다.
- 시나리오 하나에 의도 하나, 한 번의 실행 흐름이다. 기대값은 사용자가 화면에서 보는 결과로만 적는다.
- 실행 방법(쿼리·훅·명령)은 적지 않는다. 내부 값(DB 행·로그·픽셀)은 코드 테스트의 몫이다.
- 무언가를 없애는 태스크는 대신 보여야 할 것을 함께 적는다.
- 이 태스크 브랜치에서 실제로 해 볼 수 있는 것만 적는다.

## 4. Phase (medium·large — `## 개발 계획` 안)

```markdown
## 개발 계획
### Phase 1 — 로그인 API
- 파일: `src/auth/login.ts`, `src/auth/session.ts`
- 사유: 토큰 인증으로 바꾼다

### Phase 2 — 로그인 화면
- 파일:
  - `src/ui/LoginForm.tsx`
- 사유: 새 API를 화면에 잇는다
```

- `commit-task`가 Phase마다 커밋 하나를 만든다. 파일은 한 줄에 쉼표로, 또는 들여쓴 목록으로 적는다.
- Phase를 쓰면 계획 파일은 Phase의 `- 파일:`에서만 읽는다.
- 한 파일이 여러 Phase에 걸치지 않게 나눈다. 걸치면 앞 Phase 커밋에 들어가고 메시지에 "(Phase 1·2 변경 포함)"이 붙는다.
- 목록에 없는 파일(잠금 파일 등)은 마지막 Phase 커밋에 들어가고, 병합 확인 요약에 "계획 확인 뒤 추가된 파일"로 보인다.
- small은 Phase 없이 커밋 하나다.

## 5. 부속 자료

화면 캡처는 태스크 문서 옆 `screenshots/`, 목업은 `mockup/`에 둔다. 처음 쓸 때 만든다.
